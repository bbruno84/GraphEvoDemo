# V01 T1 — native rejection of the tested two-store configuration

Classification: **observed native rejection under the tested conditions**.
T2 was not executed. This is neither a data-isolation result nor an observation
of mixed A/B rows. It selects no GraphEvo 2 topology.

## Native outcome

The coordinator's console captured an uncaught `NSInvalidArgumentException`:

> Cannot assign the same iCloud Container Identifier to multiple persistent stores with the same database scope.

The app terminated with signal 6. This exception was not delivered through the
Swift `async throws` path or a persistent-store completion result. The initial
report has no `finished` timestamp, `localSaveCompleted = false`, `errors = []`
and no completed fixture observation. Its empty error array is **not evidence
of successful opening**; the process ended before it could retain a final
Swift outcome. The authoritative rejection evidence is the console exception,
correlated with the signed build and manifest, not a fabricated completed JSON.

No A/B insert operation was reached by the stage code and no local routing,
cloud replica, mapping comparison or separation conclusion was established.
Framework bookkeeping or partial files before process termination were not
certified. T2 was deliberately not launched after the rejection. No scope or
container was changed to bypass it; T3–T5 were not attempted.

## Subsequent application guard and limits

After preserving the native evidence, a minimal application preflight was added
to avoid repeating the known crash. Before constructing a cloud mirroring owner
or setting its store descriptions, it rejects duplicate pairs of CloudKit
container identifier and database scope. Descriptions without cloud options
remain valid for local-only tests. It does not choose a different scope,
container or zone. The report explicitly uses `preflightRejected`, not a new
Apple result or a native callback error; the UI describes T1 as rejected and
holds the T2 button.

The guard is committed separately as
`f51d91d511c95bda81ec0c7bd095dc83aa695b6a`. It was tested locally with an
injected owner factory proving no mirror owner is constructed for the duplicate.
The completed suite has 27 tests (all passed), with final log
`test_sim_2026-10-23T19-59-34-556Z_pid58527_35812c86.log` and result
`test_sim_2026-10-23T19-59-34-556Z_pid58527_1c4a4a69.xcresult`;
those later preflight checks are not a repeat hardware trial. No further
hardware/cloud operation is part of the guard validation.

The native observation rules out this exact two-store/same-resource/same-scope
configuration inside one container under the stated conditions. It does not
show that arbitrary other store/container/scope/sharing arrangements work or
fail, nor whether R01 can be met by another supported mapping. Those questions
remain for separately reviewed experiments. No workaround or architecture
change is adopted here. No wipe or store deletion occurred; local artifacts
and any existing remote test data remain for review.
